# ADR PI3-yaa-0002 — Go module path migration (monorepo sub-path → own module)

Status: [Accepted]
Date: 2026-06-02
PI: PI3-yaa
Deciders: yaagents-architect (ratifies user-direct decision 2026-06-02; LOCKED in
`portfolio/INTAKE/PI3-yaa-intake.md` §A-3)

## Context

PI2-yaa shipped `client-go` as a Go module under the monorepo sub-path
`github.com/ai-mpathyminds/yaagents/client-go` (v0.1.0/v0.2.0 tags applied with the
`client-go/v0.X.0` sub-path tag convention). The monorepo `gateway/` shipped under
`github.com/ai-mpathyminds/yaagents/gateway` analogously. **Neither was published publicly** —
PI2-yaa REL-* prod publish was deferred to PI3-yaa per intake §A-7.

PI3-yaa adds a NEW Go server SDK `sdk-go`, and per ADR PI3-yaa-0001 splits the monorepo into
meta-repo + 7 public submodule repos. Each Go component now needs an explicit module path that
matches its standalone submodule repo URL — `proxy.golang.org` resolves modules by their git
remote, so `github.com/ai-mpathyminds/yaagents/client-go` is no longer a valid module path once
`client-go/` lives at `github.com/ai-mpathyminds/yaagents-client-go`.

The question: how do we migrate Go module paths cleanly given v0.1.0/v0.2.0 tags from the
monorepo path exist locally (not published publicly)?

## Decision

1. **Go module paths migrate to own-module URLs** (per intake §A-3 LOCKED):

   | Component | Old path (monorepo sub-path) | New path (submodule own module) |
   |-----------|------------------------------|---------------------------------|
   | gateway   | `github.com/ai-mpathyminds/yaagents/gateway`   | `github.com/ai-mpathyminds/yaagents-gateway`   |
   | client-go | `github.com/ai-mpathyminds/yaagents/client-go` | `github.com/ai-mpathyminds/yaagents-client-go` |
   | sdk-go    | *(new)*                                          | `github.com/ai-mpathyminds/yaagents-sdk-go`    |

2. **`v0.1.0` and `v0.2.0` tags from the monorepo paths are retired.** They were applied during
   internal development but `proxy.golang.org` never indexed them because the source repo was
   PRIVATE through PI2-yaa close. No back-compat shim is needed — there are no external
   consumers of the old paths. v0.3.0 ships fresh from the new module paths.

3. **Each migrated repo's `go.mod` declares the new path** (verified at RP-{GATEWAY,SDKGO,CLIGO}-INIT
   WI close). The migration command sequence per repo:
   ```bash
   # In <component> working copy on the new submodule repo:
   sed -i '1c\module github.com/ai-mpathyminds/yaagents-<component>' go.mod
   find . -name '*.go' -exec sed -i 's|github.com/ai-mpathyminds/yaagents/<component>|github.com/ai-mpathyminds/yaagents-<component>|g' {} +
   go mod tidy
   go build ./...
   ```

4. **sdk-go adapter sub-modules** (`adapters/chi/`, `adapters/gin/`, `adapters/echo/`) carry
   their own `go.mod` files declaring sub-paths off the main module:
   - `module github.com/ai-mpathyminds/yaagents-sdk-go/adapters/chi`
   - `module github.com/ai-mpathyminds/yaagents-sdk-go/adapters/gin`
   - `module github.com/ai-mpathyminds/yaagents-sdk-go/adapters/echo`
   Sub-module isolation preserves the core `sdkgo/` zero-non-stdlib-runtime-deps constraint
   (per PRD §5.10).

5. **First public tag is `v0.3.0` on each new repo.** `proxy.golang.org` indexes within ~30 min
   of tag push (PRD §10.4 SLO; verified at SG-7 and LA-GO-CLIENT acceptance).

## Consequences

- Clean module-path identity per repo — `proxy.golang.org` resolves each module to its
  standalone submodule repo; no monorepo sub-path ambiguity.
- v0.1.x / v0.2.x Go-module artifacts (none published) are forever-frozen at the old path; OSS
  users who somehow find the old path will get module-not-found from the proxy. Acceptable
  because no public consumers exist.
- A grep audit (RP-XREF WI) sweeps the entire post-restructure source tree for any lingering
  `github.com/ai-mpathyminds/yaagents/{gateway,client-go}` references in `.go` files,
  `go.mod`, GH Actions workflows, README badges, and Compose files. RP-XREF acceptance: 0
  hits across all 8 repos.
- The sdk-go adapter sub-module pattern (each adapter has its own `go.mod`) means consumers
  who only need the core can `go get github.com/ai-mpathyminds/yaagents-sdk-go@v0.3.0` without
  pulling chi/gin/echo into their build graph. Adapter users explicitly opt in:
  `go get github.com/ai-mpathyminds/yaagents-sdk-go/adapters/chi@v0.3.0`.
- Versioning cadence after PI3-yaa: each Go submodule independently tags `v0.X.Y` going
  forward (no more lockstep requirement once components diverge in cadence). v0.3.0 is the
  initial lockstep release for the launch.

## Alternatives

- **Alternative A (rejected — keep sub-path)**: ship `github.com/ai-mpathyminds/yaagents/{gateway,client-go}`
  as the canonical Go module paths under the meta-repo. Conflicts with ADR PI3-yaa-0001's
  per-submodule shape — the submodule repo `yaagents-gateway` would carry a `go.mod` declaring
  a path that doesn't match the repo's own git remote, which `proxy.golang.org` rejects.
  Rejected on technical grounds.
- **Alternative B (rejected — major-version /v2 path)**: declare `github.com/ai-mpathyminds/yaagents/v2/{...}`
  to mark the breaking module-path change with semver discipline. Adds path complexity for
  zero consumer benefit (no public v0.x consumers exist). The `v0.X.Y` cadence with own-module
  paths is sufficient — no major-version bump required.
- **Alternative C (rejected — back-compat shim repo)**: publish a `github.com/ai-mpathyminds/yaagents`
  shim that re-exports the new module paths under the old names. Adds a maintenance surface
  for zero benefit. Rejected; non-retroactive boundary is cleaner.
