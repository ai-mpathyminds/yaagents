# ADR PI1-yaa-0002 — Agentic REST Response Profile media-type set + schema/profile versioning

Status: [Accepted]
Date: 2026-05-17
PI: PI1-yaa
Deciders: yaagents-architect

## Context

The PRD §4 fixes a normative status × media-type table (10 response types) and
mandates a `trace` block (`correlationId`, `requestId`) in every body. We must
decide: schema dialect, version-path layout, the authoritative source of the
table, and whether the `accepted` (202) async-operation flow ships a runtime in
PI1-yaa (OQ-3).

## Decision

1. **`spec/` is the single authoritative source** of the Response Profile
   prose + normative table. Every other component (schemas, OpenAPI, SDK,
   clients, CLI, gateway) references it; **none redefine or paraphrase** the
   table. The PRD §4 table is copied verbatim into `spec/`.
2. **JSON Schema Draft-07**, every schema carrying `$schema`, `$id`, `title`.
   Six schemas, one per vendor media type (PRD §5.2).
3. **Version-path layout `schemas/v0.1/`** and `spec/VERSION` = `0.1`. Profile
   header literal: `X-YAAgents-Profile: v0.1`. Every published package declares
   `Supports YAAgents Profile v0.1`. Future profile bumps add a sibling
   `schemas/vX.Y/` — never mutate a published version path.
4. **`accepted` (202) — schema ships, runtime polling deferred (resolves
   OQ-3).** `operation-accepted.schema.json` and the SDK
   `AgenticResponse.accepted(...)` factory ship in PI1-yaa so the contract is
   complete. The **async polling loop**
   (`GET /…/{opId}/status` runtime + gateway long-poll) is **v0.2 scope** — not
   built in PI1-yaa. The reference example does not exercise a 202 flow.
5. **Shared golden corpus**: one set of valid/invalid example bodies per media
   type lives under `spec/examples/` (WI-1yaa.SPEC-5) and is the single
   cross-component conformance fixture (SDK, both clients, CLI all test against
   it). Prevents per-component drift.

## Consequences

- SPEC WIs are sequenced first; every other component `depends_on` SPEC-1/2.
- The golden corpus is the de-facto contract test — a media-type change is a
  corpus change reviewed once, consumed everywhere.
- 202 surface exists in types/schemas/SDK but is untested end-to-end in
  PI1-yaa; this is an accepted, documented gap (v0.2 closes it).

## Alternatives considered

- *JSON Schema 2020-12* — rejected for v0.1: Draft-07 has the widest validator
  support across Python (`jsonschema`) and TS ecosystems for a launch.
- *No version path (`schemas/*.json` flat)* — rejected: blocks clean
  side-by-side v0.2 evolution.
- *Build the 202 polling runtime now* — rejected: out-of-scope per PRD §11
  (async-operation profile = v0.2); would expand the gateway + example.
