# ADR PI3-yaa-0001 — Meta-repo + 7 public submodule shape; `spec/schemas/openapi/examples/docs` at meta-repo root

Status: [Accepted]
Date: 2026-06-02
PI: PI3-yaa
Deciders: yaagents-architect (ratifies user-direct decision 2026-06-02; LOCKED in
`portfolio/INTAKE/PI3-yaa-intake.md` §A-1 + §A-2)

## Context

PI2-yaa shipped v0.2.0 as an Apache 2.0 monorepo (8 components under
`github.com/ai-mpathyminds/yaagents`). PI3-yaa is the public-launch PI — the source repo must go
PUBLIC and OSS users must be able to install + contribute against per-component repos.

Two repository topologies were considered:

1. **Monorepo public** — single public repo with all 8 components; one issue tracker; one CI
   pipeline; per-component sub-paths.
2. **Meta-repo + per-component submodules** — `github.com/ai-mpathyminds/yaagents` is a thin
   meta-repo containing the Profile contract + community docs; each language component lives in
   its own submodule repo (`yaagents-gateway`, `yaagents-sdk-fastapi`, `yaagents-sdk-go`, ...).

Existing portfolio precedent: `ai-platform/` already uses the meta-repo + submodules shape
(7+ submodules inside `ai-platform/`). The yaagents portfolio CLAUDE.md preamble notes
"Single repo — components are directories, **not** submodules" for the **internal** working
view, while the **public** topology is the question this ADR resolves.

Two sub-questions:
- Do `spec/`, `schemas/`, `openapi/`, `examples/`, `docs/` go into the meta-repo root or into
  their own submodule (e.g. a `yaagents-spec` repo)?
- How do Profile-version bumps propagate across submodules?

## Decision

1. **Topology = meta-repo + 7 public submodules** (per intake §A-1 LOCKED):
   ```
   github.com/ai-mpathyminds/yaagents              ← META-REPO (public)
   ├── README, LICENSE, CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, .gitmodules
   ├── spec/        schemas/        openapi/        examples/        docs/      ← root, NOT submodules
   └── submodules ×7:
       ├── gateway/         → github.com/ai-mpathyminds/yaagents-gateway
       ├── sdk-fastapi/     → github.com/ai-mpathyminds/yaagents-sdk-fastapi
       ├── sdk-go/          → github.com/ai-mpathyminds/yaagents-sdk-go          [NEW PI3-yaa]
       ├── client-python/   → github.com/ai-mpathyminds/yaagents-client-python
       ├── client-ts/       → github.com/ai-mpathyminds/yaagents-client-ts
       ├── client-go/       → github.com/ai-mpathyminds/yaagents-client-go
       └── cli/             → github.com/ai-mpathyminds/yaagents-cli
   ```

2. **`spec/`, `schemas/`, `openapi/`, `examples/`, `docs/` stay at meta-repo root** — NOT
   separate submodules (per intake §A-2 LOCKED). Rationale: they are the **Profile contract**
   that every submodule depends on. Every submodule build step fetches the canonical files via
   the meta-repo working copy. Promoting them to a submodule would force every component repo
   to carry a submodule pointer to `yaagents-spec` and create a cyclic dependency at clone time
   (gateway tests need schemas; schemas live in a sub-submodule).

3. **Profile changes ARE meta-repo events.** A Profile-version bump
   (`spec/agentic-rest-profile.md` + `schemas/v0.X/*.json` + `openapi/*.yaml`) lands as a single
   meta-repo PR; version bumps then propagate to submodules via coordinated bump PRs in each
   submodule repo (one PR per submodule citing the meta-repo SHA). This is how PI3-yaa's
   profile-v0.3 bump (WI-3yaa.SP-1) propagates to each of the 7 submodules during RP-XREF +
   per-component INIT WIs.

4. **`examples/` lives at meta-repo root** — NOT as a separate submodule, even though the
   examples are independently runnable (`docker compose up` from a single example dir). The
   examples are reference implementations that **consume** the published submodule components
   via registry installs (`pip install yaagents-fastapi`, `docker pull
   ghcr.io/ai-mpathyminds/yaagents-gateway`); they do not need to exist as a separate repo with
   its own CI/issue tracker.

5. **`docs/` (Astro Starlight Pages site source) lives at meta-repo root** — see ADR
   PI3-yaa-0004 for the GitHub Pages hosting decision. The Pages-site build workflow lives at
   meta-repo `.github/workflows/pages.yml` and references the meta-repo `docs/` source.

## Consequences

- 8 repos to administer instead of 1 (meta-repo + 7 submodules). Each carries its own
  per-component README, LICENSE, CONTRIBUTING, issue tracker, and CI workflow. Operator
  overhead is real but acceptable: each repo is small (one component scope) and the per-repo
  CI workflows are independently triggered by per-component changes (faster CI than monorepo).
- Per-component contributors get a clear scope: a community contributor authoring a new gateway
  plugin opens a PR against `yaagents-gateway`; a TS-client contributor opens against
  `yaagents-client-ts`. No need to learn the full monorepo layout.
- Profile contract changes require a meta-repo PR + 7 submodule bump PRs (cross-coordination
  cost). Mitigated by the meta-repo coordination-PR pattern: the meta-repo PR includes a
  checklist of the 7 submodule bump PRs needed; reviewer merges all 8 atomically (in practice,
  meta-repo first, then submodules cite the merged SHA).
- `.gitmodules` at meta-repo root + `git clone --recurse-submodules` workflow for users who
  want the full source tree. Users who only need a single component install from the public
  registries (PyPI/npm/GHCR/Go proxy) — no submodule operations required.
- The shape matches the portfolio precedent (`ai-platform/` uses the same meta-repo +
  submodules pattern), reducing cognitive load for portfolio-aware contributors.
- Lockstep release: at v0.3.0, all 7 submodule repos tag `v0.3.0` (or component-specific tag if
  cadence diverges later — not the case at v0.3 launch). The meta-repo also tags `v0.3.0`,
  pointing at the submodule commit SHAs.
- **No yaagents-spec submodule** means the spec evolution can be reviewed in the meta-repo's
  single context (alongside the example flows and the Pages site that documents it); avoids the
  "spec drift vs implementation" failure mode where a spec submodule advances without paired
  implementation updates.

## Alternatives

- **Alternative A (rejected — monorepo public)**: ship `github.com/ai-mpathyminds/yaagents` as
  a single public monorepo. Lower operator overhead (1 repo, 1 issue tracker) but worse
  contributor experience (contributors must learn the full monorepo layout to make a
  per-component change; CI workflow is a megamatrix that runs all components on every PR).
  Rejected per user-direct decision 2026-06-02.
- **Alternative B (rejected — meta-repo + 8 submodules including yaagents-spec)**: promote
  `spec/schemas/openapi` to a separate `yaagents-spec` submodule repo. Creates a cyclic
  dependency at clone time (gateway tests need schemas; schemas would live in a sub-submodule
  of gateway-repo, OR every component repo carries a submodule pointer to yaagents-spec adding
  N submodule operations on every clone). Rejected per intake §A-2.
- **Alternative C (deferred — standalone `yaagents/` GitHub org)**: move all 8 repos to a
  standalone `yaagents/` GitHub org (out from under the `ai-mpathyminds/` umbrella). Defers to
  v0.4+ traction gate per ADR PI3-yaa-0005; mid-launch org migration creates a path-rewrite
  cascade (Go module paths, workflow files, Trusted Publisher configs, doc links) that's
  higher cost than benefit for an unproven OSS project.
