# ADR PI3-yaa-0003 — Portfolio scrub via squashed-history orphan-baseline mirror

Status: [Accepted]
Date: 2026-06-02
PI: PI3-yaa
Deciders: yaagents-architect (ratifies user-direct decision 2026-06-02; LOCKED in
`portfolio/INTAKE/PI3-yaa-intake.md` §A-4)

## Context

PI2-yaa's internal `yaagents/` repo carries planning artifacts that **MUST NOT** appear in any
public submodule repo:

- `yaagents/docs/PI*-yaa/` (per-PI roadmaps + per-component WI breakdowns)
- `yaagents/docs/adr/PI*-yaa-*.md` (internal ADRs)
- `yaagents/system-refs/*.seed.md` (chief-architect seeds)
- `yaagents/system-refs/*_detailed.md` (full PRDs)
- `yaagents/system-refs/*_onepager.md` (PRD one-pagers)
- `yaagents/.claude/` (agent definitions; skill mirror)
- `yaagents/CLAUDE.md` (yaagents-specific Claude Code instructions)

If left in the working tree at submodule-mirror time, every `cp -r yaagents/<component>/* ./`
(per-submodule INIT WIs in `repo.md`) would leak the surrounding `docs/` or `system-refs/`
content. Even if the per-INIT WIs are careful, the meta-repo's working tree itself would still
carry the artifacts, and the meta-repo goes PUBLIC at LA-PUBLIC-FLIP.

Three sub-questions:
1. Where do the internal artifacts move to?
2. How do we ensure the **commit history** of each public submodule does not leak internal
   filenames or PR titles referencing internal PI/WI IDs?
3. How do we preserve provenance (the internal SHA the public release was derived from)?

## Decision

1. **Internal artifacts move to `portfolio/yaagents-internal/`** (per intake §A-4 LOCKED; PRD
   §7.1 mapping). The move target is in the **private** portfolio repo, NOT a public repo:
   ```
   portfolio/yaagents-internal/
   ├── docs/PI*-yaa/      ← from yaagents/docs/PI*-yaa/
   ├── adr/               ← from yaagents/docs/adr/PI*-yaa-*.md
   ├── seeds/             ← from yaagents/system-refs/*.seed.md
   └── specs/             ← from yaagents/system-refs/*_detailed.md + *_onepager.md
   ```
   `yaagents/.claude/` content is preserved under `portfolio/yaagents-internal/.claude/agents/`
   so future PI{n}-yaa planning can continue to load the yaagents-architect / yaagents
   product-manager / yaagents platform-engineer / yaagents go-developer / yaagents
   python-developer / yaagents frontend-developer agents. The yaagents-side directory is
   `git rm`'d from the working tree.
   `yaagents/CLAUDE.md` is consolidated into the portfolio-root `CLAUDE.md` `## yaagents`
   section (already mostly there as a CLAUDE.md product-table row).

2. **Per-submodule baseline = orphan-history commit** (per intake §A-4 LOCKED):
   ```bash
   # In each empty new submodule repo (github.com/ai-mpathyminds/yaagents-<component>):
   cp -r <internal-monorepo>/yaagents/<component>/* .
   # ... per-language metadata migration (go.mod / pyproject.toml / package.json) ...
   git checkout --orphan public-main
   git add -A
   git commit -m "Initial public release of yaagents-<component> v0.3.0 — squashed mirror of \
   internal monorepo at ai-mpathyminds/yaagents-internal@<sha>"
   git branch -M public-main main
   git push origin main
   ```
   Result: each public submodule repo has **exactly one commit** on `main` at v0.3.0 launch.
   No internal commit history; no internal PR titles; no internal author emails outside the
   yaagents-internal commit message.

3. **Provenance is preserved via the orphan-baseline commit message.** The `<sha>` placeholder
   in the commit message resolves to the internal monorepo's HEAD SHA at the moment of mirror.
   This gives OSS users a single reference point if they ever need to trace a v0.3.0 artifact
   back to its origin: `git log` on the public repo shows one commit; the commit message names
   the internal SHA; the internal SHA lives in the private `portfolio/yaagents-internal/`
   working tree (which is also where the `<component>/` source lived pre-mirror).

4. **Trade-off acknowledged**: OSS users **lose internal commit history**. They see one
   monolithic commit "Initial public release ..." at v0.3.0, then incremental commits going
   forward. This is acceptable per user-direct decision 2026-06-02 — OSS users need
   code+license+contributing, not internal PI narrative.

5. **Verification script**: `bin/yaagents-public-mirror-verify.sh` (authored by
   platform-engineer at A-4 per planning runbook A-4 artifact spec) greps the public submodule
   working trees for portfolio-marker strings: `.claude\|portfolio/\|PI[0-9]*-yaa\|system-refs\|CLAUDE\.md`.
   Pass condition: 0 hits (excluding CHANGELOG entries citing past version numbers, which are
   legitimate). Runs as the final gate of TRACK SCRUB AND again as B-01 PRECHECK item 5
   (operator-driven pre-LAUNCH gate) AND at LA-PI-GATE acceptance check #8.

## Consequences

- Each public submodule repo presents a clean v0.3.0 baseline to OSS users — no need for them
  to wade through internal PI/WI history.
- Future commit history is **forward-only**: incremental PRs against the public submodule
  repos accumulate normally from v0.3.0 onward. Internal portfolio work continues to happen
  in the private `portfolio/yaagents-internal/` tree, with internal SHAs cited in subsequent
  release commits when cross-referenced.
- The mirror is **one-way** (internal → public, not bidirectional). Community contributions
  to public submodules MUST be merged back into the internal `portfolio/yaagents-internal/`
  tree at a cadence the operator chooses (PI close is the natural sync point; mechanical
  `git pull` per submodule with squash-merge into the internal mirror). This is a known
  operator overhead; mitigated by community contribution cadence being low in early-stage OSS
  projects.
- The scrub verification script is **the gate**: PI3-yaa does not close on green-PI-GATE
  unless the script returns 0 hits on all 8 public repos. Adoption signal for the rule:
  PI3-yaa PC-1 acceptance + at least one mid-PI re-run of the script after any post-launch
  cross-ref work.
- No "private fork → public fork" git workflow — the orphan-baseline approach is one-shot. If
  OSS contributors propose changes against the public repos that need to land back in the
  internal tree, the operator does a manual merge (file-level), NOT a git-history merge.
  Acceptable for v0.3 launch; revisit at v0.4 if community contribution velocity warrants a
  more sophisticated sync workflow.

## Alternatives

- **Alternative A (rejected — full history mirror)**: `git push --all` from the internal monorepo
  to each public submodule repo's `main`. Preserves commit history but leaks internal PR
  titles, author emails for internal-only contributors, and internal PI/WI IDs in commit
  messages. Rejected per user-direct 2026-06-02 — the leak surface is unacceptable.
- **Alternative B (rejected — `git filter-repo` scrub)**: use `git filter-repo` to rewrite the
  internal commit history removing internal-only files and editing internal commit messages.
  Preserves enough history to be useful while scrubbing the leak surface. Rejected on
  complexity grounds: `filter-repo` rewrites are easy to get wrong (mid-rewrite errors are
  hard to recover from); the scrub criteria are subjective (which commits stay? which message
  edits?); the operator overhead is high; OSS users gain little because the early commit
  history is heavily AimpathyMinds-internal anyway. Squashed orphan-baseline is the simpler
  choice with the same outcome.
- **Alternative C (rejected — public-from-day-1)**: never run a private internal monorepo;
  develop everything in public from PI1-yaa. Rejected at PI1-yaa per ADR PI1-yaa-0004 (license
  posture meant the source was source-available not OSI, so public-from-day-1 wasn't a fit).
  Now that v0.2.0 flipped to Apache 2.0 and v0.3 ships public, going forward all new
  development can happen in the public repos directly (the mirror is one-shot, not ongoing).
