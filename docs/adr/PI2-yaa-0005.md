# ADR PI2-yaa-0005 — token-validator JWKS sourcing + prompt-sanitize stub behaviour

Status: [Accepted]
Date: 2026-05-30
PI: PI2-yaa
Deciders: yaagents-architect

> ADR PI2-yaa-0004 number is intentionally skipped to mirror the PRD §11
> citation table verbatim. The decisions otherwise covered by a 0004 ADR
> are folded into PI2-yaa-0001 (plugin lifecycle / always-on floor) and
> this ADR (the two remaining open questions).

## Context

Two open questions surfaced at PRD authoring:

- **OQ-3 — token-validator JWKS reuse**: `portfolio/packages/go/auth-jwks/`
  is targeted for extraction by PI14-oppor per `LIBRARIES.md`. If the
  extraction has landed by PI2-yaa A-3 start, the token-validator plugin
  imports it (Gate 3 `library_ref` form). If not, the plugin
  re-implements JWKS fetch + RS256 validation minimally inline (Gate 3
  `library_justify` form with explicit rationale).
- **OQ-7 — prompt-sanitize stub behaviour**: when an operator sets
  `prompt-sanitize.enabled: true` on the stub (PRD §6.5 plugin `d`),
  should the gateway (a) log-and-pass-through (treat enabled-stub as a
  developer-noted "I know it's a stub, give me the chain slot"), or (b)
  exit 1 at boot with "stub not suitable for production"?

## Decision

### Decision 1 — JWKS sourcing (resolves OQ-3)

**Verified at A-3 (2026-05-30):** `portfolio/packages/go/auth-jwks/`
does **NOT** exist. `portfolio/packages/go/` contains only `README.md`;
no `auth-jwks` subdirectory. `LIBRARIES.md` row for the extraction
proposal is re-targeted to PI14-oppor. `oppor/docs/PI14-oppor/` is also
absent — PI14-oppor has not been planned yet (oppor's `docs/` contains
PI1, PI2, PI10, PI13, adr/, ops/ as of 2026-05-30).

**token-validator plugin re-implements JWKS fetch + RS256 validation
minimally inline** under `gateway/internal/plugins/token-validator/jwks.go`.
The implementation is intentionally small: stdlib `crypto/rsa`,
`crypto/x509`, `encoding/json`, `net/http`, an in-memory keys cache
keyed on `kid` with TTL, and a stale-while-revalidate fallback (if the
JWKS server is unreachable past TTL, keep using stale keys but
warn-log). HS256 dev path stays simple stdlib.

The plugin Init signature (`Init(cfg PluginConfig) error`) is stable so
the import path can switch in a future PI when the extraction lands —
the WI body for token-validator (PLG-3 in `plugins.md`) calls this out
explicitly. The open extraction row in `LIBRARIES.md` stays open and
references token-validator + the oppor JWKS triplet as combined target
consumers (six near-identical implementations across the portfolio when
counting yaagents, oppor ×3, ai-platform ×2, platform-services/iam).

### Decision 2 — prompt-sanitize stub behaviour (resolves OQ-7)

**Log-and-pass-through, warn-once.** When `prompt-sanitize.enabled: true`
is set, the stub emits a `warn: prompt-sanitize is a stub; full
prompt-injection defence deferred to PI3-yaa or community` log line on
the first request handled by the stub (`sync.Once` guard so the warning
is not spammed); all subsequent requests pass through silently. The
gateway does **NOT** exit 1 at boot.

Rationale:
- Operators experimenting with the plugin registry (e.g. wiring a
  community sanitize plugin alongside the stub, or trialling chain
  ordering) should not be punished with a hard fail.
- The warn-log gives an audit signal — a one-line entry in journald /
  CloudWatch / Loki is enough for an SRE to spot the stub being live.
- The same posture applies to the `otel-audit` stub plugin (PRD §6.5
  plugin `e` — log warn-once when `enabled: true` AND `endpoint` is
  empty; in addition, `Init` returns non-nil error on a *malformed*
  `endpoint` URL because that is an operator config bug, not a
  stub-being-enabled choice — the `otel-audit` discriminates between
  "intentionally enabled stub" and "config error").

## Consequences

- token-validator re-implements JWKS inline; ~150 lines of stdlib Go
  under `gateway/internal/plugins/token-validator/jwks.go`. Test
  coverage budget on this code is ≥85% (matches PLG-3 acceptance).
- The future PI that extracts `portfolio/packages/go/auth-jwks/` swaps
  the import path in token-validator's `jwks.go` for a single import +
  delete the inline implementation. The plugin's external API is
  unchanged.
- `LIBRARIES.md` open extraction row gains a yaagents-side consumer
  citation (token-validator) — confirms the rule-of-three across
  products now totals 6 implementations; the extraction-now signal is
  even stronger. (Architect adds the row update via PROCESS as part of
  the PC-4 / platform-librarian feedback loop, not as a PI2-yaa engineering
  WI.)
- Both stub plugins (prompt-sanitize, otel-audit) emit warn-once log
  lines when enabled — operators get visibility without runtime cost.
  The PRD §6.5 + PRD §12 deferral to PI3-yaa or community is preserved
  unchanged.
- CLI-CONF (`conformance-test`) can optionally probe for the
  warn-once log line as evidence the stub is in the chain when the
  operator runs the conformance harness with `--require-plugin
  prompt-sanitize` — out of scope for PI2-yaa CLI-CONF (which only
  asserts the three default-on plugins) but a candidate future
  enhancement.

## Alternatives considered

- **Build a fresh `portfolio/packages/go/auth-jwks/` extraction now,
  inside PI2-yaa scope** — rejected: cross-product library extraction
  is `platform-librarian` lane work + requires consumer migration of
  oppor / ai-platform / iam under their own architects' planning; cannot
  land in a single yaa-lane PI without breaking lane discipline. The
  inline re-implementation is the minimum viable token-validator and
  keeps yaa-lane self-contained.
- **prompt-sanitize stub exits 1 when `enabled: true`** — rejected:
  hostile to operators wiring chains; the warn-once + pass-through gives
  a softer + still auditable failure mode.
- **prompt-sanitize stub returns 500 on every request when enabled** —
  rejected: would break end-to-end conformance harnesses; the stub's
  purpose is "interface in place; impl deferred", not "deliberately
  broken".
