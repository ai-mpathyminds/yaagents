# ADR PI2-yaa-0002 — ai-platform/ai-gateway absorption: shape + code lineage

Status: [Accepted]
Amended: 2026-05-30T19:30Z (user-direct: MOVE not COPY; ai-platform/ai-gateway decommission lands in PI2-yaa; breaking changes welcome — no production consumers)
Date: 2026-05-30
PI: PI2-yaa
Deciders: yaagents-architect

## Context

`ai-platform/services/ai-gateway/` is a Go reverse-proxy carrying LLM-specific
concerns (PRD §7.1: SSE streaming, per-tenant SSE concurrency limit,
execution timeout, Keycloak realm-aware JWKS, CORS, SSE Prometheus
metrics). It exists separately from `yaagents/gateway/` because v0.1.x
had no plugin model. PI2-yaa adds the plugin model (PRD §6) AND collapses
the duplication by absorbing the LLM-specialisation into yaagents.

Two open questions:

- **OQ-1 — absorption shape**: layer-atop `yaagents/gateway`
  (Option A — LLM specialisation lives inside yaagents/gateway, activated
  by config) vs sibling component `yaagents/llm-gateway` (Option B —
  separate thin binary that depends on yaagents/gateway).
- **OQ-2 — code lineage**: copy ai-platform code into yaagents under
  Apache 2.0 with attribution, OR keep ai-platform as the source and
  have yaagents consume via Go modules.

## Decision

1. **Option A (layer-atop) chosen.** LLM-specialisation lives inside
   `yaagents/gateway/`:
   - `gateway/internal/llm/` — SSE proxy (pipe-and-flush), per-tenant
     concurrency limiter, execution-timeout context wrapper, SSE
     Prometheus metrics.
   - `gateway/internal/plugins/cors/` — CORS as a first-class plugin
     (community-promotable in PI3-yaa).
   - Activation is config-driven: a route's `mode: sse` in `routes.yaml`
     opts into the SSE pipe-and-flush path; standard JSON routes are
     unaffected (the SSE code path is dormant — PRD §7.1 Option A
     trade-off accepted).

2. **Code lineage: MOVE — delete from ai-platform, absorb into yaagents.**
   (Amended 2026-05-30T19:30Z per user-direct: previous posture was
   *copy with attribution* while ai-platform/ai-gateway ran unchanged
   this PI. User confirms ai-platform/ai-gateway has **no production
   consumers**, so breaking changes are welcome and the decommission
   lands in PI2-yaa.) Specific files moved:
   - `ai-platform/services/ai-gateway/internal/proxy/sse.go` →
     `yaagents/gateway/internal/llm/sse.go`
   - `ai-platform/services/ai-gateway/internal/proxy/proxy.go` →
     `yaagents/gateway/internal/llm/proxy.go`
   - `ai-platform/services/ai-gateway/internal/metrics/sse_proxy.go` →
     `yaagents/gateway/internal/llm/metrics.go`

   Each moved file gets the standard SPDX header per LIC-2 — the
   attribution-comment requirement is dropped (the originating commit
   hash is preserved by git history of the ai-platform-side `git rm`
   commit; no narrative comment in the file is required). The
   ai-platform-side deletion (`services/ai-gateway/` + its compose
   entry + its deploy workflow + its `portfolio/infrastructure/` TF
   block) is a **cross-lane direction** routed to chief-architect at
   PI2-yaa A-3 handoff — it cannot land from the yaa-lane yaagents-architect
   pen.

2a. **Breaking changes welcome (new).** With no production consumers
   on ai-platform/ai-gateway, the absorbed LLM-specialisation may
   freely change config field names, route paths, env-var naming, and
   any other public surface. The yaagents-canonical names already
   chosen by the WI bodies (`max_sse_connections_per_tenant`,
   `mode: sse`, `executionTimeoutSeconds`, `yaagents_gateway_sse_*`
   metrics, plain `jwks_url` without Keycloak-realm interpolation) win;
   no backward-compat shims for `KEYCLOAK_REALM` / `MaxSSEConnectionsPerTenant`
   / `/api/v1/agents/...` route shapes are required.

3. **Why not go-modules-consume from ai-platform** (OQ-2 negation):
   inverting the dependency would force yaagents (a public OSS repo) to
   depend on `ai-platform` (a private monorepo path). That kills the
   "yaagents is the BASE" architecture established by ADR PI1-yaa-0001
   and prevents the future re-base direction (internal gateways adopt
   the yaagents gateway, not the reverse).

## Consequences

- The standard-mode `yaagents-gateway:0.2.0` image carries the SSE code
  path; it is dormant unless a route declares `mode: sse`. Acceptable:
  &lt;1 KLOC additional code; no runtime overhead when no SSE route is
  registered (the SSE path is selected at routes-load time, not per-
  request).
- The example at `examples/llm-gateway/` (PRD §7.2) proves the absorption
  has a working consumer; PI2-yaa close gate (`PI-GATE`) verifies all 5
  PRD §13.2 flows.
- **ai-platform/services/ai-gateway/ is deleted in PI2-yaa** (cross-lane
  direction at chief-architect — see Addendum). The "future plt-aip PI"
  consumer-migration line in the original Consequences is REMOVED.
- The attribution-comment requirement on absorbed files is DROPPED.
  Files carry the standard SPDX header per LIC-2 only. Git history of
  the ai-platform-side `git rm` commit preserves the originating commit
  pointer for archaeology.
- The PRD §12 row "ai-platform/ai-gateway ECS service changes →
  service runs unchanged this PI" is **superseded** by this amendment.
  Product-manager should update PRD §12 at the next PRD revision (not
  blocking — the ADR is the binding contract).

## Alternatives considered

- **Option B (sibling `yaagents/llm-gateway`)** — rejected: doubles the
  release surface (two GHCR images) and forces operators choosing
  between standard + LLM mode to swap images instead of flipping config.
  The clean refactor argument ("LLM concerns don't pollute gateway core")
  does not hold — Option A keeps LLM code in its own `internal/llm/`
  package, just inside the same binary.
- **go-modules-consume from ai-platform** — rejected: inverts the
  intended dependency direction; couples public OSS to a private repo;
  blocks ADR PI1-yaa-0001's "yaagents is the BASE" posture.
- **Re-implement LLM specialisation from scratch in yaagents** — rejected:
  the ai-platform code is production-tested; re-implementing introduces
  regression risk for no benefit. MOVE (post-amendment) preserves the
  exact source + tests; ai-platform side gets `git rm`'d so the code
  exists in exactly one place.

## Addendum 2026-05-30T19:30Z — User-direct: MOVE not COPY

User confirmed at PI2-yaa A-3 that ai-platform/ai-gateway has **no production
consumers**, so the original "copy with attribution; ai-platform runs
unchanged this PI" posture is reversed. The MOVE flips three things:

1. **Files are MOVED, not COPIED.** Same target paths; the ai-platform-side
   originals are deleted in the same PI.
2. **ai-platform/ai-gateway is decommissioned in PI2-yaa scope.** Consumer
   migration concern is trivially N/A (no consumers exist). The
   ai-platform-side cleanup spans: `ai-platform/services/ai-gateway/`
   (delete), `ai-platform/docker-compose.yml` (remove the ai-gateway
   service block), `ai-platform/.github/workflows/ai-gateway-deploy.yml`
   (delete), and `portfolio/infrastructure/roots/compute/` ai-gateway
   ECS module + ALB rules + ECR repo + SSM parameters (delete via
   platform-engineer-portfolio).
3. **Breaking changes welcome.** No backward-compat shims for the old
   ai-platform/ai-gateway public surface (route paths, env-var names,
   config field names, metric prefixes, Keycloak-realm interpolation
   semantics). yaagents-canonical naming is the single source of truth.

### Cross-lane direction (routed at A-3 handoff)

The yaa-lane yaagents-architect lane CANNOT delete from ai-platform or
portfolio/infrastructure. The ai-platform-side decommission requires a
chief-architect cross-lane direction that fans out to:

- **ai-platform-architect** (plt-aip lane): a small ai-platform PI WI
  (or a chief-architect-seeded mini-roadmap) that does `git rm -rf
  services/ai-gateway/`, removes the compose entry, deletes the deploy
  workflow.
- **platform-engineer-portfolio** (portfolio lane): a TF cleanup PR that
  removes the ai-gateway ECS module, ALB target group + listener rule,
  ECR repository, SSM parameter group, and any IAM roles scoped to the
  service. The TF deletion plan should appear in `terraform plan` before
  apply.

These cross-lane WIs are NOT enumerated in `yaagents/docs/PI2-yaa/`
(out of writable lane); they are surfaced to chief-architect via the
`> blocker:` handoff at A-3 turn close. yaagents-side absorption
(LLM-1..4 + EX-LLM-1..3) is fully self-contained and can proceed in
parallel.
