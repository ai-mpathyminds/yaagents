# ADR PI3-yaa-0005 — GitHub org branding: stay at `ai-mpathyminds/yaagents-*` for v0.3 launch

Status: [Accepted]
Date: 2026-06-02
PI: PI3-yaa
Deciders: yaagents-architect (ratifies user-direct decision 2026-06-02; LOCKED in
`portfolio/INTAKE/PI3-yaa-intake.md` §A-6)

## Context

PI3-yaa is the public-launch PI for yaagents. The repos go PUBLIC and the packages publish to
prod registries (PyPI, npm, GHCR, Go module proxy). A question that arises at the moment of
public-flip: which GitHub org owns the repos long-term?

Two paths:

1. **Stay at `ai-mpathyminds/yaagents-*`** — repos live under the existing AimpathyMinds
   GitHub org. Module paths: `github.com/ai-mpathyminds/yaagents-<component>`. Package scope:
   `@aimpathyminds/yaagents-client` for npm. GHCR images: `ghcr.io/ai-mpathyminds/yaagents-gateway`.
2. **Move to standalone `yaagents/` GitHub org** — create new GitHub org `yaagents/`; transfer
   the repos out from under `ai-mpathyminds/`. Module paths become `github.com/yaagents/<component>`;
   npm scope `@yaagents/client`; GHCR `ghcr.io/yaagents/<component>`.

Standalone-org positioning carries community signal: "this is a standalone OSS project, not an
AimpathyMinds-internal tool". Counter-positioning: "this is an AimpathyMinds open-source
contribution" — equally valid for an early-stage launch where the company brand carries the
launch credibility.

The question: does the standalone-org move happen at v0.3 (concurrent with public flip), or
later?

## Decision

1. **Stay at `ai-mpathyminds/yaagents-*` for v0.3 launch** (per intake §A-6 LOCKED). All 8
   repos (1 meta + 7 submodules) live under the `ai-mpathyminds/` GitHub org at v0.3.0.

2. **Module / package / registry paths follow the org**:
   - Go modules: `github.com/ai-mpathyminds/yaagents-{gateway,sdk-fastapi,sdk-go,client-python,client-ts,client-go,cli}` (see ADR PI3-yaa-0002 + ADR PI3-yaa-0001)
   - PyPI packages: `yaagents-fastapi`, `yaagents-client`, `yaagents-cli` (package names are scope-less; the org affiliation appears on PyPI's "Maintainer" field, not the package name)
   - npm: `@aimpathyminds/yaagents-client` (scope = `@aimpathyminds`)
   - GHCR: `ghcr.io/ai-mpathyminds/yaagents-gateway`

3. **Standalone `yaagents/` GitHub org deferred to v0.4+ traction gate.** Decision criteria
   for re-opening the discussion (any of):
   - GitHub repo passes 500 stars
   - External (non-AimpathyMinds) contributor count ≥10
   - Community demand surfaces in GitHub Discussions / Issues
   - Strategic reason (e.g. a non-AimpathyMinds-affiliated maintainer joins)

4. **Why "not at v0.3"**: mid-launch org migration creates a path-rewrite cascade:
   - All 8 repo URLs change (`github.com/ai-mpathyminds/yaagents` → `github.com/yaagents/yaagents`).
     `gh repo transfer` handles the redirect for git operations, but cached URLs in documentation
     / README badges / external blogs would need updates.
   - Go module paths change → all internal imports across 8 repos need rewrite; downstream
     consumers (ai-platform/agent-api canary; future community plugin authors) hit
     module-not-found errors on the old paths.
   - PyPI Trusted Publisher configs (B-01 PRECHECK item 1) would need re-configuration for the
     new repo paths.
   - npm scope change (`@aimpathyminds/yaagents-client` → `@yaagents/client`) is a hard break;
     `npm deprecate @aimpathyminds/yaagents-client` + republish under new scope.
   - GHCR image path change.
   - GitHub Actions workflow files — registry URLs, OIDC `sub` conditions
     (`repo:ai-mpathyminds/yaagents-*` → `repo:yaagents/yaagents-*`).
   - Pages site URL — `ai-mpathyminds.github.io/yaagents/` → `yaagents.github.io/yaagents/`
     (ADR PI3-yaa-0004 Astro config change).
   - Documentation: every install command in every README + Quickstart + Profile Spec page.

   Compounding all of this at the moment of public-launch is high risk for low benefit on an
   unproven OSS project. The cost is real; the benefit is community-signal-driven and depends
   on traction that doesn't exist yet.

5. **Migration path when triggered** (future-PI scope, NOT v0.3):
   - Operator creates `yaagents/` GitHub org.
   - `gh repo transfer ai-mpathyminds/yaagents{,-gateway,-sdk-fastapi,-sdk-go,-client-python,-client-ts,-client-go,-cli} --to yaagents` (1 meta + 7 submodules).
   - Per-Go-module path rewrite (8 repos × `sed -i 's|github.com/ai-mpathyminds/yaagents-|github.com/yaagents/yaagents-|g'`).
   - npm scope migration (deprecate old scope; republish under new).
   - PyPI Trusted Publisher reconfiguration.
   - GHCR image republish OR re-tag.
   - Pages site Astro config update.
   - Documentation sweep.
   This is its own WI (or set of WIs) in the future PI; expected scope ~1 sprint of dedicated
   work.

## Consequences

- v0.3 launch sticks with the **existing** ai-mpathyminds GitHub org, OIDC trust configs, npm
  scope, and GHCR namespace. Zero path-rewrite cost at launch.
- The "AimpathyMinds open-source project" framing dominates v0.3 community messaging — the
  README + Pages site clearly attribute yaagents as an AimpathyMinds contribution. This is
  honest framing for an early-stage launch.
- Future-PI migration cost is acknowledged and planned-for. The migration is **not free**, but
  it is **deferred** until the community-signal benefit clearly justifies the engineering
  cost.
- npm scope `@aimpathyminds` is locked at launch — once published, the scope can't be silently
  renamed. Any future migration to `@yaagents` is a hard republish + deprecate + community
  comm cycle. This is the largest single cost of deferring the org decision; weighed against
  the org-move cost incurred mid-launch, it remains the right trade.
- ADR PI3-yaa-0001 (per-submodule repo shape) + ADR PI3-yaa-0002 (Go module path migration)
  are SHAPE decisions independent of the ORG decision; if/when the standalone-org move
  happens, those shapes carry forward unchanged (only the org segment of each path mutates).
- Trusted Publisher / NODE_AUTH_TOKEN / GHCR org-package-settings (B-01 PRECHECK) are all
  configured for the `ai-mpathyminds/` org at v0.3. Re-configuring on org move is part of the
  future-PI migration scope.

## Alternatives

- **Alternative A (rejected — move org at v0.3 launch)**: standalone `yaagents/` GitHub org at
  v0.3.0. Strong community-signal positioning but high path-rewrite cost concurrent with
  launch (see Decision §4 cascade). Rejected per user-direct 2026-06-02 — too much risk
  bundling at the launch moment.
- **Alternative B (rejected — move org one PI after launch, fixed schedule)**: ship v0.3 under
  `ai-mpathyminds/`, then move to `yaagents/` at v0.4 unconditionally. Fixed-schedule rejects
  the traction-signal discipline; ties future-PI scope to a question whose answer depends on
  community response that doesn't exist yet. Rejected on planning grounds.
- **Alternative C (rejected — never move org)**: stay at `ai-mpathyminds/` forever. Locks the
  project into the company-brand framing; removes the option to standalone if traction
  warrants. Rejected on optionality grounds — the deferral here is reversible; the locked-in
  decision is not.
