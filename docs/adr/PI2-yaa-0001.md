# ADR PI2-yaa-0001 — Plugin interface contract + versioning + registration

Status: [Accepted]
Date: 2026-05-30
PI: PI2-yaa
Deciders: yaagents-architect

## Context

PI2-yaa introduces a plugin middleware system to replace the PI1-yaa
hardcoded `auth → tenant → RBAC → audit` chain (PRD §6). Open question
OQ-6 asks how the plugin interface declares its own version: a `Version()
string` method on the interface vs Go module-tag versioning. The decision
also has to cover how plugins register (static-import side-effect vs
dynamic loading) — the security floor (PRD §10 `[SEC]`) requires a clear
answer because `plugin.Open()` / `dlopen` allow runtime code injection.

## Decision

1. **No `Version() string` method on the `Plugin` interface.** Plugin
   versioning is by **Go module tag** — the plugin contract lives at
   `github.com/ai-mpathyminds/yaagents/gateway/plugin` and is versioned
   with the gateway repo (`gateway/plugin/v0.2`). If the interface ever
   needs a non-additive change, that is a `gateway/plugin/v1` module
   path (semver-major Go modules import-path versioning convention).

2. **Declaration order = execution order.** Plugins are listed in the
   YAML `plugins:` block; their `Handler(next)` is composed in that
   order, with the innermost handler closest to upstream. PRD §6.4 — the
   gateway core does not reorder plugins.

3. **Static import-side-effect registration.** Plugins call
   `plugin.Register(&MyPlugin{})` from an `init()` function in their
   package. The gateway operator builds a binary that imports both
   yaagents/gateway and the community plugin module; the plugin is wired
   by import side-effect. The gateway will **NEVER** call `plugin.Open()`
   or `dlopen` — dynamic loading is rejected as a security floor
   violation (PRD §10 `[SEC]` Gateway plugin sandboxing). Community
   plugins ship as Go modules consumed at build time; operators take
   responsibility for the binaries they build.

4. **Reverse-order Shutdown.** On SIGTERM, `plugin.Shutdown(ctx)` is
   called in reverse declaration order (PRD §6.4) so plugins observing
   "I'm being shut down first" can tear down dependencies before the
   plugins they themselves depend on are gone.

5. **Always-on floor.** `token-validator` (plugin `a`) is the security
   floor — its `enabled: true` flag CANNOT be set to `false`. The
   gateway core asserts this at boot AND the plugin itself rejects a
   `false` config in its own `Init` (defence-in-depth).

## Consequences

- Plugin authors version via their own Go module tags; no compat matrix
  encoded in the runtime. Major bumps to the plugin contract require a
  new import path (`gateway/plugin/v1`), which the operator-side build
  surfaces explicitly.
- Community plugins compile into a custom operator binary; the
  yaagents-published image
  (`ghcr.io/ai-mpathyminds/yaagents-gateway:0.2.0`) contains only the
  five first-party plugins. Operators who need extras build their own
  image FROM the yaagents image with `RUN go build` injected, OR a
  full-source rebuild. README in PI3-yaa should document both shapes.
- The no-`plugin.Open` posture is verified by CI grep
  (`grep -rn "plugin.Open\|dlopen" gateway/` returns 0).
- Token-validator always-on is enforced at two layers — gateway core
  rejects YAML at boot; plugin itself rejects disabled config. Either
  alone would close the floor; both together is intentional.

## Alternatives considered

- **`Version() string` on the interface** — rejected: couples plugin
  authors to a method signature that adds no value beyond the Go module
  tag they already publish. Compat-checking based on string equality
  becomes a separate, less idiomatic mini-protocol.
- **Dynamic plugin loading via `plugin.Open`** — rejected: opens a
  runtime-code-injection attack surface; Go's `plugin` package has
  well-known portability + GLIBC-version issues; the community plugin
  story does not require it (Go-modules consumption is idiomatic + safer).
- **Forward-order Shutdown** — rejected: plugins later in the chain
  often depend on plugins earlier in the chain (e.g. otel-audit's tracer
  depends on the JSON-logger plugin's context); reverse-order Shutdown
  matches teardown-before-dependency convention.
