# Typed Outcome Model <Badge text="Stable" variant="success" />

The typed outcome model is the core discipline of the yaagents Agentic REST Profile.
Instead of returning arbitrary JSON, every agentic endpoint returns one of **10 normative
response types** — each with a fixed HTTP status code and a vendor `Content-Type` header
the caller can dispatch on.

This page tables all 10 types, grounded in the `sdk-fastapi` `AgenticResponse` source
(`sdk-fastapi/src/yaagents_fastapi/response.py`), with exact method signatures.

---

## The 7 agentic outcome types

These are the outcomes specific to agentic behavior — they encode domain-meaningful
states that don't exist in plain CRUD APIs.

| Type | HTTP | Content-Type | Meaning | `AgenticResponse` method |
|------|------|-------------|---------|--------------------------|
| **success** | 200 | `application/json` | Sync result ready; domain-defined body | `AgenticResponse.success(body, *, correlation_id, request_id)` |
| **created** | 201 | `application/json` | Agent produced a new resource | `AgenticResponse.created(body, *, correlation_id, request_id)` |
| **accepted** | 202 | `application/vnd.yaagents.operation+json` | Async — operation queued; poll `statusUrl` | `AgenticResponse.accepted(operation_id, status_url, *, message, correlation_id, request_id)` |
| **clarification_required** | 400 | `application/vnd.yaagents.clarification+json` | Agent needs more input from the caller | `AgenticResponse.clarification_required(required_inputs, *, message, code, correlation_id, request_id)` |
| **validation_failed** | 422 | `application/vnd.yaagents.validation-error+json` | Request inputs failed validation | `AgenticResponse.validation_failed(errors, *, message, code, correlation_id, request_id)` |
| **approval_required** | 412 | `application/vnd.yaagents.approval-required+json` | High-consequence action needs human sign-off | `AgenticResponse.approval_required(approval_token, *, message, code, correlation_id, request_id)` |
| **conflict** | 409 | `application/vnd.yaagents.conflict+json` | Requested action conflicts with existing state | `AgenticResponse.conflict(*, code, message, conflicting_resource_id, correlation_id, request_id)` |

## The 3 infrastructure outcome types

These encode gateway-layer and service-layer failures — they reuse `application/vnd.yaagents.error+json`
because they are infrastructure outcomes, not domain-specific agentic outcomes.

| Type | HTTP | Content-Type | Meaning | `AgenticResponse` method |
|------|------|-------------|---------|--------------------------|
| **forbidden** | 403 | `application/vnd.yaagents.error+json` | RBAC / scope rejection | `AgenticResponse.forbidden(*, code, message, correlation_id, request_id)` |
| **failed_dependency** | 424 | `application/vnd.yaagents.error+json` | Required upstream dependency failed | `AgenticResponse.failed_dependency(*, code, message, correlation_id, request_id)` |
| **error** | 500 | `application/vnd.yaagents.error+json` | Unhandled internal error | `AgenticResponse.error(*, code, message, correlation_id, request_id)` |

## The `trace` block

Every vendor-typed response body (`application/vnd.yaagents.*+json`) carries a mandatory
`trace` block:

```json
{
  "type": "clarification_required",
  "code": "CLARIFICATION_REQUIRED",
  "message": "Please specify a target audience segment.",
  "requiredInputs": [...],
  "trace": {
    "correlationId": "corr-abc123",
    "requestId": "req-xyz789"
  }
}
```

For `success` and `created` (`application/json`), the `trace` block is **recommended**
and injected only when non-empty IDs are passed to the factory method.

---

## When to use `clarification_required` vs `validation_failed`

| Scenario | Use |
|----------|-----|
| Input format is wrong (missing required field, wrong type) | `validation_failed` (422) |
| Input format is correct but agent cannot proceed without more context | `clarification_required` (400) |
| "campaign goal is ambiguous — do you mean CTR or revenue?" | `clarification_required` |
| "budget field must be a positive number" | `validation_failed` |

The campaign-api example demonstrates both patterns in `POST /campaigns/{id}/optimizations`.
